# ADR-0012: Входи правил і перевірок адресують тип артефакту, а не етап

- **Status:** Proposed
- **Date:** 2026-10-08
- **Supersedes:** —
- **Related:** ADR-0009 (D1: `swot_errc_cycle` — один вузол; модуль узгодженості), ADR-0010 (D6: перевірки виконує ml), ADR-0011 (Q1, Q3, Q6: id артефактів, замикання `refs`, версії канви в рядку циклу), `bizstruct-ml` ADR-0001 (правило `gather_inputs`)

> Це нотатка з дизайну. Код, версія й схеми **не змінюються**. Після рішення мейнтейнера її приймає окремий PR.

---

## Context

`RuleInput` називає **етап** (`stage: Stage`) і кратність (`ONE` / `MANY`). Правила й перевірки судді читають **артефакти**, а етап не дорівнює одному типу артефакту. Зі слайсу 2 `bizstruct-ml` (PR #8) це перестало бути теорією: `gather_inputs` уже збирає входи для живих перевірок, і три випадки не виражаються.

### Проблема 1. Етап `swot_errc_cycle` тримає `Swot` і `Errc`, до того ж по кілька

Рядок циклу містить до п'яти `Swot` (по одному на версію канви) і до чотирьох `Errc` (ADR-0009, ADR-0011 Q6). Вхід `RuleInput(stage=SWOT_ERRC_CYCLE, arity=ONE)` не каже ні *який тип*, ні *яка версія*.

- `errc_move_targets_correct_canvas_version` і `swot_environment_scan_reference_is_known` мають по одному такому входу, але стосуються різних типів (`Errc`, `Swot`).
- `pitch_risk_analysis_grounded_in_swot` хоче **фінальний** `Swot`.
- Правило ml сьогодні розрізняє тип лише за анотацією параметра функції `check` (`expected_types_of`). У `JudgeCheck` функції немає, анотації теж: `run_judge` викликає `gather_inputs` без типів. Тож для `pitch_risk_analysis_grounded_in_swot` пул `SWOT_ERRC_CYCLE` містить і `Swot`, і `Errc` (завершений цикл містить щонайменше один `Swot` і один `Errc`), і `gather_inputs` кидає «ambiguous input». Перевірку неможливо виконати на жодному реальному циклі. Це видно з коду (`core/context.py`, гілка `ONE`), не з запуску: етап `swot_errc_cycle` ще не реалізовано.
- Навіть із відомим типом «один `Swot`» двозначне: версій до п'яти.

### Проблема 2. Версії канви 2..5 лежать у рядку циклу

За ADR-0011 Q1/Q6 стартова `Canvas` v1 належить рядку `canvas`, а v2..v5 — рядку `swot_errc_cycle`. Етап `canvas` у `RuleInput` означає «артефакти етапу canvas», тобто лише v1. Усе інше залежить від того, як реалізований збирач:

- ml зіставляє артефакт із етапом за **класом моделі** (`ARTIFACT_STAGE`), тому канви v2..5 «знаходяться», якщо рядок циклу випадково в зоні видимості (власні артефакти, прямі `refs`, замикання). Контракт домену цього не гарантує.
- Для `future_scenario_references_nonempty_sections` і `storytelling_references_nonempty_sections` потрібна **фінальна** канва. Їхній рядок посилається лише на рядок циклу (ADR-0011 Q2), тож під прямими `refs` є тільки v2..5; якщо цикл закінчився на v1 (критерій зупинки лишив «останню кращу»), фінальна канва лежить у рядку `canvas`, якого немає серед прямих `refs`. Збирач «ONE із прямих `refs`» (ADR-0001) тоді повертає «немає канви» або, при двох і більше версіях у циклі, «неоднозначно».
- `errc_move_targets_correct_canvas_version` просить «усі версії канви цієї групи» (`MANY`). Мова «етап canvas» цього не каже.

### Проблема 3. `multi_sided_requires_signal` бере сигнал з будь-якого сценарію проєкту

Правило перевіряє `any(s.interdependence_signal for s in customer_scenarios)` по **всіх** сценаріях, які отримав на вхід (рядок `patterns` посилається на всі). У проєкті, розбитому на кілька канв, тег `multi_sided_platform` у групі B задовольняється сигналом зі сценарію групи A. Методологія (крок 4 Patterns) вимагає сигнал у парі **всередині компоненти**.

## Decision

### D1. `RuleInput` називає тип артефакту

```python
class Arity(StrEnum):          # замінює StageArity
    ONE   = "one"    # рівно один екземпляр; їх кілька — помилка неоднозначності
    MANY  = "many"   # список усіх екземплярів у межах групи (див. D3)
    EACH  = "each"   # перевірка виконується окремо для кожного екземпляра
    FINAL = "final"  # фінальна версія версійованого артефакту (canvas, swot)

class RuleInput(SanitizedModel):
    artifact: ArtifactType
    arity: Arity
    optional: bool = False

    @property
    def stage(self) -> Stage:          # домашній етап: ARTIFACT_STAGE[artifact]
        ...
```

- `artifact` замінює `stage`. `stage` лишається **обчислюваною властивістю** (домашній етап) для читачів, яким потрібен етап; конструктор із `stage=` зникає.
- `EACH` — відповідь на повторювані екземпляри одного типу в рядку (`Errc` ×4, `Swot` ×5): виконавець викликає `check` по одному разу на кожний екземпляр цього входу, решта входів збирається один раз. `ONE` лишається суворим (неоднозначність — `ContextError`).
- `FINAL` визначає домен чистою функцією (D2).

### D2. Що таке «фінальний»

- **Canvas:** `is_final == True`. Рівно одна фінальна версія в родині канви (v1..vN однієї групи), інакше `ContextError`.
- **Swot:** `Swot` із `canvas_id`, що збігається з id фінальної канви. Фінальний `Swot` не обов'язково з найбільшою версією: критерій зупинки (BMG-методологія) лишає «останню кращу», а не щойно згенеровану.
- `Errc` не має `FINAL` (допустимі `ONE`, `MANY`, `EACH`).

Домен дає чисті функції `final_canvas(canvases)` і `final_swot(swots, canvases)`; збирач не повторює логіку. **Хто виставляє `is_final`**, ADR-0010 каже лише «система» (be або оркестратор): це відкрите питання нижче, і `FINAL` не працює, доки воно не вирішене.

### D3. Звідки читається артефакт: «власники» типу

Кожен тип має **власників** — етапи, у рядках яких він може лежати:

```python
ARTIFACT_HOLDERS: dict[ArtifactType, tuple[Stage, ...]] = {
    ...  # усі типи: (ARTIFACT_STAGE[t],)
    ArtifactType.CANVAS: (Stage.CANVAS, Stage.SWOT_ERRC_CYCLE),   # v1 / v2..5 (ADR-0011 Q1)
}
```

Правило збирання (домен фіксує, ml реалізує; це розвиток правила з ml ADR-0001 «прямі `refs`, інакше замикання, плюс власні артефакти»):

1. Кандидати типу `T` = **власні артефакти свіжого рядка** типу `T` (вони замінюють збережені застарілі) +, для **кожного власника** `H` типу `T`:
   - якщо `refs` свіжого рядка називають етап `H`: артефакти типу `T` із рядків, названих під `H`; кожен має існувати, бути `DONE` і мати артефакти, інакше `ContextError`;
   - інакше: артефакти типу `T` із `DONE`-рядків етапу `H` у замиканні (свіжий рядок виключено).
2. Тип відбирається **за типом артефакту**, не за етапом рядка. Анотації параметрів `check` більше не потрібні (`expected_types_of` зникає).
3. Кратність застосовується до кандидатів: `ONE` — рівно один (0 → `ContextError`, якщо вхід не `optional`; ≥ 2 → неоднозначність); `MANY` — усі; `EACH` — усі, з розгортанням у цикл; `FINAL` — `final_canvas` / `final_swot` над кандидатами (для `Swot` кандидати канв збираються тим самим правилом).
4. Для `ONE` лишається чинним прямий збирач ADR-0001 (свіже + прямі `refs`, без замикання); замикання потрібне лише для `MANY`/`FINAL`/`EACH` там, де власник не названий у `refs`.

Для випадку «канва v1 є фінальною» правило 1 бере v1 із замикання (власник `canvas` не названий у `refs` рядка `storytelling`), а v2..5 — з прямих `refs` (власник `swot_errc_cycle` названий). Один вхід `FINAL` покриває обидва.

### D4. Вплив на `is_checkable` і `applies_to`

`is_checkable(completed: set[Stage])` лишає сигнатуру (ml і далі рахує `completed` із `DONE`-рядків замикання). Змінюється те, що вхід вимагає:

| вхід | потрібні завершені етапи |
|---|---|
| `ONE`, `MANY`, `EACH` | домашній етап типу, `ARTIFACT_STAGE[artifact]` |
| `FINAL` | `swot_errc_cycle` (фінальна позначка існує лише після циклу) |

Опційні входи працюють як сьогодні: якщо правило має опційні входи, завершеним має бути щонайменше один із них. `applies_to` (етапи, чий свіжий рядок може запустити перевірку) = домашні етапи входів; для типів із кількома власниками і кратностями `MANY`/`FINAL`/`EACH` — ще й усі власники (тобто `swot_errc_cycle` для `canvas`). Зайве спрацювання нешкідливе, бо `completed` рахується із замикання свіжого рядка, де нижчі етапи недоступні.

### D5. Виправлення проблеми 3

Входи правила не змінюються (`customer_scenario MANY`, `patterns ONE`): група визначена **вмістом** `Patterns`, а `CustomerScenario.empathy_map_id` зв'язує сценарій із `CanvasGroup.empathy_map_ids`. Виправляється тіло:

```python
def multi_sided_requires_signal(customer_scenarios, patterns):
    by_map = {s.empathy_map_id: s for s in customer_scenarios}
    for group in patterns.groups:
        if group.relation_type != MULTI_SIDED:
            continue
        scenarios = [by_map[i] for i in group.empathy_map_ids if i in by_map]
        if not any(s.interdependence_signal for s in scenarios):
            violation(group, ids=[patterns.id, *(s.id for s in scenarios)])
```

- Умова спрацювання — **група з `relation_type == MULTI_SIDED`**, а не наявність тегу. Підстава: у методології `multi_sided` для групи означає пару з сигналом взаємозалежності; тег `multi_sided_platform` валідатор `Patterns` і так прив'язує до такої групи. Це **розширення** поведінки (правило перевіряє й групу без тегу); мінімальний варіант, що зберігає поточну умову «лише коли є тег», але рахує сигнал лише по сценаріях MULTI_SIDED-груп, — варіант A нижче.
- Сценарій, якого немає серед отриманих (`by_map` без запису), не вважається джерелом сигналу; відсутність сценаріїв групи — помилка `ContextError` на боці збирача, а не тихий пропуск (у `patterns` усі сценарії лежать у прямих `refs`).
- Повідомлення називає групу (її id і `empathy_map_ids`), щоб зворотний зв'язок повтору був точним.
- Тести в домені: сигнал лише в групі A, тег/група multi-sided у групі B → помилка; сигнал у групі B → без помилки; одна група → як раніше.

Варіант A: умова лишається «є тег»; помилка, якщо жоден сценарій **усіх** MULTI_SIDED-груп не має сигналу. Слабше: група B без сигналу поряд із групою A із сигналом проходить. Рекомендовано D5 (по групі).

## Migration of the 12 checks

Усі 6 детермінованих правил і 6 перевірок судді. `ONE` у стовпці «сьогодні» — це `RuleInput(stage=…, arity=ONE)`.

| # | перевірка | сьогодні | пропонується | зміна | виражається? |
|---|---|---|---|---|---|
| 1 | `multi_sided_requires_signal` | `customer_scenario MANY`, `patterns ONE` | ті самі (`customer_scenario MANY`, `patterns ONE`) | **тіло** за D5 | так |
| 2 | `canvas_group_id_is_known` | `patterns ONE`, `canvas ONE` | `patterns ONE`, `canvas EACH` | перевіряє `group_id` кожної версії, не лише v1 | так (`ONE` теж коректне й лишає v1) |
| 3 | `future_scenario_references_nonempty_sections` | `canvas ONE`, `future_scenario ONE` | `canvas FINAL`, `future_scenario ONE` | неоднозначна → фінальна | так, потребує `is_final` |
| 4 | `errc_move_targets_correct_canvas_version` | `canvas MANY`, `swot_errc_cycle ONE` | `canvas MANY`, `errc EACH` | тип явний; по одному виклику на `Errc` | так |
| 5 | `swot_environment_scan_reference_is_known` | `swot_errc_cycle ONE`, `environment_scan ONE` | `swot EACH`, `environment_scan ONE` | тип явний; перевіряється кожен `Swot` | так |
| 6 | `storytelling_references_nonempty_sections` | `canvas ONE`, `storytelling ONE` | `canvas FINAL`, `storytelling ONE` | неоднозначна → фінальна | так, потребує `is_final` |
| 7 | `empathy_map_customer_scenario_persona_consistency` | `empathy_map ONE`, `customer_scenario ONE` | без змін | — | так |
| 8 | `canvas_grounded_in_customer_insights` | `empathy_map MANY`, `customer_scenario MANY`, `canvas ONE` | без змін | група = `refs` рядка канви (D3), `canvas ONE` = v1 свіжого рядка | так |
| 9 | `pitch_risk_analysis_grounded_in_swot` | `swot_errc_cycle ONE`, `pitch ONE` | `swot FINAL`, `pitch ONE` | усуває неоднозначність Swot/Errc і версій | так, потребує `is_final` |

(`?` — `optional=True`.)

Побічні наслідки: ключі JSON входів у промпті судді для #3, #6, #9 лишаються `canvas` / `swot` (тип артефакту, а не `swot_errc_cycle`), тож `instruction` перевірки #9 («one Swot») нарешті відповідає даним.

### Що не виражається

- **Порівняння сусідніх версій** (наприклад, що `Errc.result_canvas_id` справді вказує на v(n+1) і що ходи застосовано): потрібен вхід «канва за id із поля іншого входу». Адресація за посиланням не підтримується; сьогодні правило #4 вирішує це тілом, отримавши `canvas MANY` і шукаючи за `canvas_id`. Нового правила цього виду зараз немає; якщо з'явиться, воно повторить схему #4.
- **Звуження `MANY` до групи, коли `refs` рядка не називають етап**: наприклад, правило на рядку `patterns`, що хоче лише карти однієї групи. Виражається лише тілом (як D5). Усі поточні випадки мають групу, визначену `refs` (канва) або всім проєктом (patterns).
- **`FINAL` до вирішення, хто виставляє `is_final`** (відкрите питання 1): входи #3, #6, #9 не можна виконати.
- Перевірки на **завершених нижчих етапах під час регенерації вищого** (звинувачення вищого етапу, ADR-0011 відкрите питання 3) лишаються поза обсягом.

## Consequences

- **Ламаюча зміна домену** (кандидат на 0.16.0): зникає `StageArity` і `RuleInput(stage=…)`, з'являються `Arity`, `RuleInput(artifact=…)`, `ARTIFACT_HOLDERS`, `final_canvas`, `final_swot`. Єдиний споживач реєстру — `bizstruct-ml`; `bizstruct-be` не використовує `RuleInput`.
- **ml:** `gather_inputs` переписується за D3 (по власниках, за типом артефакту); `expected_types_of` та анотаційна звірка видаляються; `EACH` розгортається у `run_deterministic` (і в судді, якщо така перевірка з'явиться); `completed_stages`/`applicable_*` читають `applies_to` за D4. Правило ml ADR-0001 про `MANY` («прямі `refs`, інакше замикання») стає окремим випадком D3.
- **be:** без змін контракту; але має виставляти `is_final` (питання 1) і зберігати `Canvas` v2..5 у рядку циклу, як у ADR-0011 Q1.
- **Тести:** уся реєстрова частина (таблиця вище) покривається тестами домену на форму входів; перевірки по групі (D5) — на чисту функцію; `FINAL` — на `final_canvas`/`final_swot` (нуль, одна, кілька фінальних; фінальна не остання версія).

## Alternatives considered

- **Додати `artifact` поряд зі `stage`** (необов'язкове поле): не ламає API, але лишає два джерела істини; `JudgeCheck` без `artifact` лишається неоднозначним. Відхилено.
- **Розділити `swot_errc_cycle` на два етапи `swot` і `errc`:** суперечить ADR-0009 D1 («один вузол»), ламає стейт-машину і `StageRow`. Відхилено.
- **Лишити розрізнення типу в ml (анотації `check`):** працює для правил, не для декларативних `JudgeCheck`; не прибирає неоднозначності версій. Відхилено.
- **Додати рядок канви до `refs` рядків `storytelling`/`future_scenario`/`pitch`** (щоб v1 була серед прямих `refs`): простіший збирач, але змінює ADR-0011 Q2, граф залежностей і be. Відхилено на користь D3.
- **`FINAL` як «найбільша `version`»:** хибне, бо критерій зупинки лишає останню *кращу* версію, а не останню.

## Deferred, and why it must be decided before the experiments

Не входить у цю зміну, але має бути вирішено **до початку експериментів** (перший прогін `pilot`/`main`):

1. **NetScore у коді.** Зараз ваги, пороги й арифметика парних оцінок живуть у промпті ml (стартова пропозиція проєкту, не з книги), а структурну коректність перевіряє тимчасовий `stages/patterns_validation.py`. Якщо NetScore перейде в домен після початку експериментів, зміниться саме те, що вимірюється (розподіл груп, тегів, кількості канв), а контроль змінних вимагає незмінного визначення в усіх чотирьох конфігураціях (A–D). Тому рішення — до першого прогону; прогони до й після перенесення непорівнянні.
2. **Закриті переліки міток (label enums).** NetScore порівнює «той самий тип каналів / відносин», «протилежні цінові рівні». `channel_type` і `relationship_type` у `CustomerScenario` — вільні рядки (методологія сама зазначає, що класифікатора немає); без закритих переліків правило детерміновано не обчислити, а вимірювання «збіглося / не збіглося» залежить від того, як модель написала слово. `PricingTier` уже enum.
3. **Тип покупця.** Четвертий доданок конфлікту (−1, B2C проти B2B з несумісними каналами) не застосовується: ознаки у домені немає. Практичний діапазон конфлікту стає −6..0, тоді як ADR-0009 каже, що пороги відкалібровано під −7..0. Треба або додати ознаку, або формально вилучити доданок з методу й перекалібрувати.

Пов'язане, але окреме: у живому прогоні слайсу 2 (PR #8 ml) NetScore не розділив дві непов'язані лінії бізнесу (оцінка synergy 1 / conflict 0 → одна канва `diversified`), бо жоден конфліктний доданок не спрацював. Це підтверджує, що (1)–(3) впливають на результат, а не лише на реалізацію.

## Відкриті питання

1. **Хто виставляє `Canvas.is_final`** (be після `StageResult` циклу чи ml у результаті)? ADR-0010 каже лише «система». Без відповіді `FINAL` не виконується.
2. Чи приймати розширення D5 (перевіряти кожну MULTI_SIDED-групу незалежно від тегу), чи залишити варіант A?
3. Номер версії: `0.16.0` (ламаюча зміна реєстру) разом зі зміною тіла правила #1 чи окремими версіями?
4. `canvas_group_id_is_known` на `EACH` (рядок #2): чи потрібна перевірка v2..5, чи достатньо v1?
